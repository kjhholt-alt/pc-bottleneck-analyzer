# The Agent-Workstation Bottleneck Hierarchy: RAM > Cores > Disk > GPU

Every "best PC for AI" build guide leads with the GPU. For most AI *inference* workloads, that is correct — the graphics card holds the model and does the math. But there is a fast-growing workload where that entire priority order flips upside down: running a **fleet of API-driven agents** — Claude Code sessions, browser automations, research agents — where the model lives in someone else's datacenter and your machine only orchestrates.

For that workload, we measured the bottleneck order directly (see [what 40 parallel Claude Code sessions cost](/blog/what-40-parallel-claude-code-sessions-cost-your-pc-2026)). It is:

**RAM > Cores > Disk > GPU.**

The GPU is dead last. This guide explains each tier, why it sits where it does, and how to spend a build budget accordingly.

---

> **TL;DR**
> - An API-agent fleet does its heavy math in the cloud. Locally, you are running orchestration processes, not a model.
> - **RAM is tier 1** because capacity caps how many agents run at once (~145 MB per session measured) and running out means a hard stutter cliff.
> - **Cores are tier 2** because agents *trigger* real local work — builds, tests, git — and cores let that run in parallel.
> - **Disk is tier 3** because agents read and write files constantly; a fast NVMe keeps tool calls snappy.
> - **The GPU is tier 4** — a spectator for API agents. On our rig VRAM never passed 6.6 GB of 24 GB.
> - Build order: max out RAM, then cores, then a good NVMe, and buy the cheapest GPU that drives your monitors.

---

## Why the usual order is wrong here

The standard AI build assumes *local inference*: the model weights sit in VRAM, and every token is generated by your GPU. Under that assumption, GPU memory and bandwidth are everything, and a 70-billion-parameter model needs 40 GB or more of VRAM just to load ([LocalLLM.in](https://localllm.in/blog/llamacpp-vram-requirements-for-local-llms)).

API-driven agents break that assumption completely. When Claude Code answers you, the inference runs on Anthropic's hardware. Your PC's job is:

- Hold the agent process and its runtime in memory
- Keep a working copy of your repo and context in memory
- Run any MCP tool servers the agent spawns
- Execute the shell commands, builds, and tests the agent requests
- Read and write files, and talk to git

Not one of those steps uses the GPU. So the components that matter are the ones that hold state (RAM), run parallel local jobs (cores), and move files (disk). The GPU falls off the list.

Let's walk the tiers.

---

## Tier 1 — RAM: the hard ceiling

**Why it is first:** RAM is the resource you run out of first, and running out of it is the worst failure mode you can hit.

On our test rig — a Ryzen 7 5700X3D with 32 GB of DDR4 — a fleet of 39 Claude Code sessions plus 8 workers held about **5.5 GB of resident memory**, roughly **145 MB per session**. Add the OS, a browser, an editor, Discord, and maybe a local database, and system RAM sat at **72% of 32 GB**. That was the binding constraint — the tool estimated only about **23 more sessions** of headroom before the machine would start paging to disk.

That last part is the whole reason RAM wins. Consider the two ways a machine runs out of a resource:

- **Out of cores:** work queues. Everything finishes *later*. Recoverable, gradual.
- **Out of RAM:** Windows starts swapping memory to the page file on disk, which is orders of magnitude slower than RAM. Agent sessions stall mid-response, tool calls time out, and — because they all hit the wall together — the entire fleet hitches at once. It is a cliff, not a slope.

**The math you actually care about:**

```
sessions you can run  ≈  (total RAM − OS/apps overhead) / cost-per-session
```

With 32 GB, budgeting ~10 GB for Windows plus your normal apps leaves ~22 GB for agents. At 145 MB each that is roughly 150 lean sessions on paper — but real sessions with MCP servers and large repos in memory cost more, which is why the *measured* headroom was tighter. The lesson: **capacity is your parallelism budget.**

**What to buy:** 32 GB is the practical floor for real agent work. Go 64 GB if you want to run large fleets or keep heavy apps open alongside. And run **dual-channel** — a single stick roughly halves memory bandwidth and shows up as system-wide sluggishness (our [RAM bottleneck guide](/blog/ram-bottleneck-signs-diagnosis-and-fixes-for-2026) has the full diagnosis). Capacity beats speed here: 64 GB of ordinary DDR5 beats 32 GB of fast DDR5 for this workload, every time.

---

## Tier 2 — Cores: parallel local work

**Why it is second:** the agents themselves are light, but they *set off* real work on your machine, and that work is what loads the CPU.

An idle agent waiting on the API uses almost no CPU. But the moment it runs a build, a test suite, a type-check, a linter, or a big git operation, that is a genuine CPU job — and in a fleet, dozens of those can fire at once. On our rig CPU ran a **43% median with a 54% peak**, comfortable at 39 sessions precisely because most were waiting on the network at any given instant. Kick off 20 simultaneous builds and that picture changes fast.

Cores are how you absorb those bursts without everything queueing. The Ryzen 7 5700X3D's 8 cores / 16 threads handled the load with room to spare; if your agents do heavy compilation, more cores (12–16) pay off directly. See [how many cores you actually need](/blog/how-many-cpu-cores-for-gaming-2026) for the general trade-offs — for agent fleets, lean toward more cores than a pure gaming build would.

**What to buy:** 8 cores is a fine floor. If your agent work is build- and test-heavy (compiled languages, large monorepos), 12–16 cores meaningfully reduces how long the fleet spends waiting on itself.

---

## Tier 3 — Disk: the constant I/O

**Why it is third:** agents live in your filesystem. They read files to build context, write files to make changes, and hammer git. That is a steady stream of small random reads and writes.

A fast **NVMe SSD** keeps all of that low-latency, so tool calls return quickly and builds pull their inputs fast. A SATA SSD works but adds latency you will feel across a big fleet; a spinning hard drive is a non-starter for this workload. This is also where RAM and disk interact: when you *do* run low on RAM and the system starts paging, a fast NVMe makes the swap thrashing less catastrophic — though the real fix is more RAM, not faster swap.

**What to buy:** a mainstream Gen4 NVMe drive is plenty. You do not need the fastest Gen5 drive on the market — capacity and reliability matter more than peak sequential numbers, because agent I/O is mostly small and random, not big sequential transfers.

---

## Tier 4 — GPU: the spectator

**Why it is last:** for API-driven agents, the GPU does nothing.

On our rig the RTX 3090 — 24 GB of GDDR6X, a card that cost more than the rest of the build combined — sat with **VRAM never exceeding 6.6 GB** and its compute mostly idle throughout heavy agent use. The fleet's inference was happening in the cloud; locally there was simply nothing for the GPU to compute. It was drawing power to render a desktop, nothing more.

This is the most common and most expensive mistake in agent-workstation builds: **pouring the budget into the graphics card.** For a fleet of API agents, that money buys you nothing. The same dollars spent on RAM and cores would have raised your ceiling directly.

**The one exception:** if you *also* plan to run models **locally** — grunt models for cheap bulk work, private inference, image generation, fine-tuning — then the GPU roars back to relevance, and VRAM capacity becomes the gate (a 70B model needs 40 GB+ of VRAM at 4-bit). That is a genuinely different machine, and we cover exactly when it is worth it in [the DGX Spark honest take](/blog/dgx-spark-honest-take-local-inference-vs-api-agent-fleets-2026). But for pure API orchestration, buy the cheapest card that drives your monitors and move on.

## Putting it together: how to spend the budget

If your machine's primary job is running an agent fleet, here is how the dollars should fall:

| Priority | Component | Target | Why |
|---|---|---|---|
| 1 | RAM | 32 GB min, 64 GB ideal, dual-channel | Caps parallelism; running out is a hard cliff |
| 2 | CPU cores | 8 min, 12–16 for build-heavy work | Absorbs bursts of builds/tests without queueing |
| 3 | NVMe SSD | Mainstream Gen4, generous capacity | Constant small-random file and git I/O |
| 4 | GPU | Cheapest that drives your displays | Idle for API agents — unless you run models locally |

Compare that to a gaming build, where the order is almost exactly reversed (GPU first, then CPU, then RAM), and you can see why generic "AI PC" advice leads people astray. **Match the build to the workload.** An API-agent fleet is a RAM-and-cores machine wearing a gaming case.

## FAQ

### What is the biggest bottleneck for running AI agents locally?
For API-driven agents (Claude Code, browser automations), it is **RAM**. Each session costs roughly 145 MB of resident memory measured, so capacity caps how many you can run at once — and running out triggers disk paging that stalls the whole fleet. The GPU is almost never the limit for this workload.

### Do I need a powerful GPU to run Claude Code or other coding agents?
No. The model runs in the cloud, so the GPU stays idle. On our test rig VRAM never passed 6.6 GB of 24 GB. Buy the cheapest card that drives your monitors and put the budget into RAM and cores instead.

### How is an agent workstation different from an AI inference workstation?
An inference workstation runs the model *locally*, so it needs a big GPU with lots of VRAM. An agent workstation orchestrates *cloud* models, so it needs RAM (to hold many sessions), cores (to run the builds and tests agents trigger), and fast storage. Opposite priority orders.

### Is 32 GB of RAM enough for an agent fleet?
It is the practical floor. 32 GB comfortably runs dozens of sessions plus normal apps. If you want to run very large fleets or keep heavy applications open alongside, step up to 64 GB — capacity is your parallelism budget.

### When does the GPU actually matter for AI work?
Only when you run models locally: local inference with open-weight models, fine-tuning, or image/video generation. Then VRAM capacity becomes the gate. For pure API orchestration, the GPU is a spectator.
