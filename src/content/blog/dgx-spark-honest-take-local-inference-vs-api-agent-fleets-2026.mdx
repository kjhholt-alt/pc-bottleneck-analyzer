# DGX Spark Honest Take: When Local Inference Beats the API for Fleet Work

In the first two articles of this series we measured an API-driven agent fleet and found it barely touches the GPU — [40 parallel Claude Code sessions](/blog/what-40-parallel-claude-code-sessions-cost-your-pc-2026) cost about 5.5 GB of RAM and left a 24 GB card idle, because the model runs in the cloud. The [bottleneck hierarchy](/blog/agent-workstation-bottleneck-hierarchy-ram-cores-disk-gpu-2026) came out RAM > cores > disk > GPU.

So here is the obvious question: if API agents don't need a GPU at all, why would anyone spend $4,000 on NVIDIA's **DGX Spark** — a desktop box built entirely around local AI inference?

The honest answer is: **for most fleet work, you wouldn't.** But there is a specific, real workload where a 128 GB local-inference appliance genuinely beats paying per API call — and it is exactly the workload people misjudge, because the DGX Spark's headline single-user benchmarks make it look worse than it is. Let's separate the hype from the honest use case.

---

> **TL;DR**
> - **DGX Spark** = GB10 Grace Blackwell superchip, **128 GB unified memory**, ~1 petaFLOP FP4, $3,999 starting (retail up to ~$5,400), shipped October 2025 ([NVIDIA](https://www.nvidia.com/en-eu/products/workstations/dgx-spark/)).
> - Its 128 GB lets it hold models a 24 GB card can't — up to 200B parameters locally.
> - **But** its memory bandwidth is only ~273 GB/s, so **single-stream** token generation is slow — about 38 tokens/sec on a 120B model, slower than three used RTX 3090s.
> - The twist: **concurrent/batched** throughput scales up to **120x** single-stream. That is the *exact* pattern an agent fleet uses — fan out to many parallel sub-tasks.
> - **Verdict:** not a chat box, not a frontier-model replacement. It is a **batch grunt-work appliance**. If your fleet fires thousands of cheap, repetitive local calls, it can beat the API on cost and rate limits. For a few agents, stick with the API.

## First: for most agent work, the API wins

Let's not bury this. If you run a handful of coding or research agents, **paying per API call is the right answer**, and it is not close:

- **You get frontier models.** The best cloud models are larger and smarter than anything you can run on a desk. No local box matches them.
- **Zero capex, zero maintenance.** No $4,000 up front, no model management, no thermal or power headaches.
- **Your PC stays cheap.** As we measured, orchestrating cloud agents needs RAM and cores, not a GPU. A modest machine runs dozens of sessions.

For the vast majority of people reading this, that is the end of the story: use the API, spend your hardware budget on RAM, done. So when does local inference actually earn its keep?

## The workload where local wins: grunt work at volume

The case for local inference is not "replace your smart agent." It is **"stop paying frontier-model prices for dumb, repetitive sub-tasks."**

A mature agent fleet does not just have a few smart agents. It fans out. One orchestrator kicks off hundreds or thousands of small, mechanical calls: classify this file, extract fields from this page, summarize this diff, label this record, transform this blob of text. Individually each is trivial — a 7B or 13B open-weight "grunt model" handles it fine. But at volume, three things bite you on the API:

1. **Cost.** Thousands of calls per run, many runs per day, adds up — even at cheap per-token rates, for work a small local model could do for the price of electricity.
2. **Rate limits.** Fan out aggressively enough and you hit throughput caps and start queueing.
3. **Data boundaries.** Some data you would simply rather not send off the machine.

This is the grunt lane. And it is where a local box with enough memory to hold a capable model — and enough *concurrency* to run many requests at once — changes the math. The doctrine we run our own fleet by is exactly this: **frontier model for architecture, cheap models for grunt work.** Local inference is how you take the grunt lane off the meter entirely.

## Where the DGX Spark fits — and where it embarrasses itself

The DGX Spark's headline spec is **128 GB of unified LPDDR5X memory** on a GB10 Grace Blackwell superchip (a Blackwell GPU fused to a 20-core Arm CPU), rated at up to **1 petaFLOP of FP4 AI performance**, for a starting price of **$3,999** ([NVIDIA](https://www.nvidia.com/en-eu/products/workstations/dgx-spark/), [NVIDIA hardware docs](https://docs.nvidia.com/dgx/dgx-spark/hardware.html)). It shipped in October 2025 and can hold models up to **200 billion parameters** in a single unit.

That memory is the point. A consumer RTX 3090 has 24 GB of VRAM — enough for models up to roughly 32B at 4-bit, but a 70B model needs about 40 GB or more just for its weights ([LocalLLM.in](https://localllm.in/blog/llamacpp-vram-requirements-for-local-llms), [Kaitchup](https://kaitchup.substack.com/p/run-llama-31-70b-instruct-on-your)). The Spark's 128 GB holds 70B, 120B, even 200B models that no single consumer card can fit.

**Now the part the marketing skips.** That unified memory runs at only about **273 GB/s** — modest next to a discrete GPU's GDDR6X. Token generation is memory-bandwidth-bound, so for a **single stream**, the Spark is slow. On the 120B GPT-OSS model it manages roughly **1,723 tokens/sec of prompt processing but only about 38 tokens/sec of generation** — and a budget rig of three used RTX 3090s generates around **124 tokens/sec on the same model, more than three times faster**, precisely because the cards' aggregate bandwidth beats the Spark's 273 GB/s ([Dendro Logic](https://dendro-logic.com/engineering/nvidia-dgx-spark-concurrency-benchmark/), [aimultiple](https://aimultiple.com/dgx-spark-alternatives)).

If you buy a DGX Spark to be a fast single-user chatbot, you will be disappointed. That is the honest warning. **It is not that.**

## The concurrency twist that changes the verdict

Here is the number that reframes the whole device. Token generation is bottlenecked by *reading the model weights from memory* — and when you run many requests at once, you read those same weights once and serve all of them. The overhead amortizes. So batched throughput scales almost linearly until you hit KV-cache or compute limits.

Measured on the DGX Spark ([Dendro Logic](https://dendro-logic.com/engineering/nvidia-dgx-spark-concurrency-benchmark/)):

| Model | Single-stream | Peak (concurrency 256) | Multiplier |
|---|---|---|---|
| Nemotron Super 49B NVFP4 | 5.79 tok/s | 695 tok/s | **120x** |
| GPT-OSS 120B MXFP4 | 33.5 tok/s | 863 tok/s | **25.7x** |

Read that again. The device that looked slow at one stream delivers **up to 120 times the throughput under concurrency.** And concurrent fan-out is *exactly* what an agent fleet does. The same benchmark author reports a real pipeline — extracting structured data from job listings — that got a **30x wall-clock speedup** moving from sequential 9B inference to parallel 120B execution, and got *better* answers because the bigger model reasoned better.

The Dendro Logic conclusion is blunt and correct: the DGX Spark's design target is **"batched extraction/transformation pipelines"** and **"agentic systems that fan out to concurrent sub-tasks"** — not single-user chat. Which is to say: the grunt lane of an agent fleet is the one workload it is actually built for.

## The decision framework

Put it together and the choice is not "API vs local" — it is three lanes:

| Your workload | Best tool | Why |
|---|---|---|
| A few smart agents; architecture, hard reasoning | **Cloud API** | Frontier quality, zero capex, GPU stays idle |
| Occasional local model; up to ~32B; private/offline | **Consumer GPU (24 GB)** | Cheap, fast single-stream, fits mid-size models |
| High-volume grunt fan-out; big models; thousands of calls/run | **DGX Spark (128 GB)** | Holds 70B–200B, batched throughput scales up to 120x, takes the grunt lane off the API meter |

The honest cost logic: a DGX Spark is roughly **$4,000 of capex**. That is a lot of API tokens. It only pays back if you are running enough repetitive local inference that the *avoided* API spend (plus dodged rate limits and kept-home data) clears $4,000 over the machine's life. For a hobbyist fleet, it won't. For someone running batch extraction, classification, or transformation pipelines at scale, day after day, it can — and the 128 GB is what lets those pipelines use a genuinely capable model instead of a toy.

## So — is it worth it?

For **most** readers of this series: **no.** Run your agents on the API, spend your money on RAM and cores, and let the cloud do the inference. That is the measured, boring, correct answer for a small fleet.

For the **specific** operator running a high-volume grunt lane — thousands of cheap, parallel, repetitive model calls, ideally on data you would rather keep local — the DGX Spark is a legitimately interesting appliance, *if* you understand what you are buying: a **concurrent batch-inference box**, not a fast chatbot. Judge it by its concurrency numbers, not its single-stream ones, and it fits the agent-fleet fan-out pattern better than almost anything else at its price and footprint.

Buy it for the workload it is built for, and it delivers. Buy it expecting a fast local ChatGPT, and you bought the wrong box.

## FAQ

### Is the NVIDIA DGX Spark worth it for AI development?
It depends entirely on your workload. For running a few cloud-API agents, no — the GPU stays idle and your money is better spent on RAM. It becomes worth it only if you run **high-volume local inference**: batched, concurrent grunt-work pipelines (extraction, classification, transformation) where its 128 GB of memory and up-to-120x concurrent throughput take that work off the API meter.

### Why is the DGX Spark slower than RTX 3090s in benchmarks?
Token generation is limited by memory bandwidth, and the Spark's unified LPDDR5X runs at about 273 GB/s — lower than a discrete GPU's GDDR6X. For a single stream it generates roughly 38 tokens/sec on a 120B model, versus about 124 tokens/sec for three RTX 3090s. But under heavy concurrency the Spark's throughput scales up to 120x, which is where it is meant to run.

### When does local inference beat paying for an API?
When you fan out thousands of cheap, repetitive sub-tasks that a small open-weight model can handle. At that volume, API cost and rate limits add up, and a fixed-cost local box doing the grunt work wins — while you still send the hard reasoning to a frontier cloud model.

### How much memory do you need to run a 70B model locally?
Roughly 40 GB or more of memory just for the weights at 4-bit quantization, and 42–48 GB with KV cache and context. A 24 GB consumer GPU can't fit it; the DGX Spark's 128 GB can, along with models up to 200B parameters.

### Should I buy a DGX Spark to run Claude Code or cloud agents?
No. Cloud agents like Claude Code run their inference in the datacenter — your machine only orchestrates, and needs RAM and cores, not a local inference box. The DGX Spark is for running models *yourself*, at volume.
